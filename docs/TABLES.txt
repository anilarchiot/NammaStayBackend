NAMMASTAY DATABASE TABLES - OPERATOR GUIDE
==========================================

Purpose
-------
This guide covers the 97 application tables created by the numbered SQL files
in supabase/migrations/. It explains what each table stores and how to work
with it safely. It is not a replacement for the SQL migration files or a
column-by-column data dictionary.

IMPORTANT SAFETY RULES
---------------------
1. Do not create, rename, truncate, or manually edit application tables in
   Supabase Table Editor. Use the NammaStay website for normal changes.
2. The website calls database functions (RPCs) for protected operations.
   These functions enforce property membership, roles, permissions,
   subscriptions, validation, and booking rules. Direct table edits can bypass
   these rules or leave related records inconsistent.
3. Most business data belongs to a property. Never move a row to another
   property by changing property_id. The database uses property-scoped
   relationships and security policies.
4. Money fields ending in _paise are integer paise, not rupees.
   Example: Rs 700.00 is stored as 70000. Do not divide or multiply stored
   values when using the NammaStay screens.
5. Guest identification, staff documents, credentials, and payment secrets
   are sensitive. Do not export or share them unnecessarily. Storage buckets
   and Supabase Auth are managed separately from the tables listed here.
6. An SQL migration is not a data-entry script. Never re-run an older setup
   bundle or a migration on a live project just to "make sure"; check first.

HOW TO APPLY SQL
---------------
Existing Supabase project:
  a. Run supabase/setup/checks/4_check_which_updates_to_run.sql in SQL Editor.
  b. For each false result, run the matching numbered file from
     supabase/migrations/, in ascending numeric order.
  c. 038_booking_page.sql and 042_staff.sql are optional features. Run them
     only if you intend to use those features.
  d. Run supabase/tests/01_security_checks.sql after the updates.

New Supabase project:
  a. Run the numbered migration files in ascending order. Migration numbers
     004 and 005 are reserved for setup tasks and are not in migrations/.
     Migration 038 (booking page) and 042 (staff) may be skipped if unused.
  b. Follow docs/GO-LIVE.md for creating the first Auth user, running the
     property seed, configuring secrets, and optional schedules.
  c. Run the security checks before entering real guest data.

The root-level SETUP_ALL.sql files are old bundles and do not contain the
current schema. Use supabase/migrations/ as the current SQL source of truth.
Do not apply this guide's table list as SQL.

TABLE CATALOG
-------------

CORE PROPERTY, ROOM, GUEST AND BOOKING DATA
-------------------------------------------

properties
  Migration: 001_schema.sql; later migrations add property settings.
  Stores each hostel, hotel, homestay, PG, or resort as a property record.
  Update details in Settings or the relevant property screen, not by changing
  its ID or kind directly.

property_members
  Migration: 001_schema.sql.
  Links Supabase Auth users to properties and stores their roles and access.
  Invite/remove staff and change roles through the team controls. Do not
  manually add a member to grant access.

rooms
  Migration: 001_schema.sql.
  Stores the room or dorm/room-type group belonging to a property.
  Create, rename, and sort rooms from Rooms & Beds. Check for bookings before
  removing a room; use the app's delete flow.

beds
  Migration: 001_schema.sql; 014 adds guest-capacity fields.
  Stores bookable units (beds for hostels, rooms/units for other property
  types), their labels, rates, status, and capacity.
  Manage units and rates from Rooms & Beds. Do not reuse/delete a unit with
  booking history unless the app permits the operation.

bed_blocks
  Migration: 001_schema.sql; 020 adds OTA-feed linkage.
  Holds a unit out of service for maintenance or an imported OTA calendar
  block. Add/remove blocks from the calendar or OTA screens, not SQL. Overlap
  constraints help prevent conflicting blocks.

guests
  Migration: 001_schema.sql; 009, 010, and 024 add guest/profile fields.
  Stores a property's guest profile and limited identity-document metadata.
  Add/edit/delete guests through guest and booking screens. Identity documents
  are sensitive; do not put full Aadhaar numbers in notes.

bookings
  Migration: 001_schema.sql; later migrations add booking features.
  Main reservation record: guest, unit, dates, totals, status, source, and
  check-in details. Create, edit, cancel, check in, and check out only through
  the booking/calendar screens and their RPCs. The database prevents
  overlapping reservations.

payments
  Migration: 001_schema.sql.
  Append-only ledger of guest payments and refunds attached to bookings.
  Record money from the booking screen. Never edit or delete a payment row;
  correct a mistake with the supported refund/correction flow.

notifications
  Migration: 001_schema.sql.
  In-app reminders and activity notices for users/property workflows.
  The app and scheduled functions manage these records; do not use them as a
  general notes table.

audit_log
  Migration: 001_schema.sql.
  Security/audit trail of important property actions. Treat as read-only.
  Do not delete entries to hide a change.

PLATFORM ADMIN, LEADS AND SUBSCRIPTIONS
---------------------------------------

platform_admins
  Migration: 006_marketing.sql.
  Allow-list of accounts permitted to use NammaStay platform-admin screens.
  Only an existing platform administrator should grant/revoke this access
  using the documented admin setup process.

leads
  Migration: 006_marketing.sql.
  Contact requests submitted through the public marketing site.
  Review and update lead status in the Leads admin screen.

platform_settings
  Migration: 007_subscriptions.sql.
  Single platform-wide billing/settings row: trial/grace periods, support
  details, and the platform's subscription-payment instructions. Configure
  in admin billing settings. Never place a service-role credential here.

plans
  Migration: 007_subscriptions.sql; 015 and 019 add plan types/pricing.
  Publicly readable subscription plan catalogue and prices.
  Maintain plans in the admin billing screen. Price values are in paise.

subscriptions
  Migration: 007_subscriptions.sql; 011 adds suspension fields.
  One subscription/access-state record per property. Admin screens and
  subscription functions manage trial, paid, complimentary, grace, and
  suspended states. Do not manually extend access by editing dates.

subscription_payments
  Migration: 007_subscriptions.sql.
  Owner-submitted subscription payment claims and admin review results.
  Submit UTRs from Billing and approve/reject them from admin billing.

property_invites
  Migration: 013_admin_add_property.sql.
  Invitation/link records used when an admin provisions a property for an
  owner who may sign up later. Use the admin property workflow.

EXTRAS, INVOICES, EXPENSES AND PAYMENT LINKS
--------------------------------------------

extra_items
  Migration: 016_extras.sql.
  A property's reusable catalogue of add-ons such as food or laundry.
  Maintain the catalogue in Settings/Extras; charges for an actual stay are
  recorded separately.

booking_charges
  Migration: 016_extras.sql.
  Extra item quantities and charges attached to a booking. Add/remove them
  through the booking detail screen so totals and invoices stay consistent.

invoice_counters
  Migration: 018_invoice_offers.sql.
  Per-property sequence/counter used to issue unique guest invoice numbers.
  Internal bookkeeping only; never reset or edit the counter manually.

invoices
  Migration: 018_invoice_offers.sql.
  Guest invoices/receipts associated with bookings and property billing
  details. Create and view them from the booking/invoice screens.

expenses
  Migration: 021_expenses_paylinks.sql.
  Property operating expenses used in profit and reporting calculations.
  Add or correct expenses from Expenses & Profit; enter dates and amounts
  carefully because reports aggregate this table.

property_secrets
  Migration: 021_expenses_paylinks.sql.
  Encrypted/restricted property integration credentials, including payment
  provider secrets. Manage them only through the relevant settings screen.
  Never query, export, or expose secret values in the frontend.

payment_links
  Migration: 021_expenses_paylinks.sql.
  Online payment-link records and provider state associated with guest
  bookings. Create/check links from booking detail; webhook/function code
  updates payment status.

PUBLIC API
----------

api_keys
  Migration: 029_public_api.sql.
  Property API key metadata, scopes, and a one-way hash of each key. Create
  and revoke keys in Settings > API keys. The full key is shown once; store
  it securely. Never add a key to public frontend source code.

api_requests
  Migration: 029_public_api.sql.
  Short-lived API rate-limit/request tracking records. Managed automatically
  by the API functions.

api_idempotency
  Migration: 029_public_api.sql.
  Stores responses for idempotent API booking requests so retries do not
  create duplicate bookings. Managed automatically by the API functions.

TABLES THAT DO NOT EXIST
------------------------
Branches do not have a separate branches table. A branch is represented as
its own row in properties, with access managed through property_members and
the branch RPCs added by 043_branches.sql.

045_public_property_count.sql creates a read-only aggregate RPC, not a table.
035_fix_upi_check.sql corrects validation constraints; it creates no table.
Supabase Auth users and Storage objects/buckets are managed by Supabase and
are not part of the 97 application tables listed above.
